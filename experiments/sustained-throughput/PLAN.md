# Sustained H100 RMSNorm throughput with four-row tiling

This is the implementation draft for [issue #64](https://github.com/hyscodebase/h100-rmsnorm-lab/issues/64). Issue #62 showed that the two-row/four-warp candidate was 1.2% slower than the fastest one-row kernel at widths 4,104 and 4,112, and gained only 1.9–3.1% at widths 4,103 and 4,105. Its one-second host telemetry had zero median GPU and memory busy despite short high-activity peaks. This experiment adds a four-row tile and a separately measured long replay window.

## Frozen experiment question

At 32,768 BF16 rows, does Triton four-warps/four-rows per program process logical input-plus-output bytes at least 5% faster than both the fastest one-row Triton kernel and shape-specialized `torch.compile`, in all three fresh seeds and all four nearby widths?

- Candidate: four warps, four rows per program.
- References: four-warps/one-row Triton, eight-warps/one-row Triton, and `torch.compile`.
- Shapes: 32,768 × 4,103, 4,104, 4,105, or 4,112; seeds 50–52.
- Correctness: every backend passes eight fixtures and the timed input against FP32 at `rtol=0.005, atol=1e-6`, plus the established cross-check at `rtol=0.016, atol=1e-5`. Every output is checked again after latency replay and after its long replay phase.
- Decision: the candidate must exceed both comparators by at least 5% on the preregistered logical-throughput metric in all three seeds. The existing 1,024-row recommendation is not modified by this experiment.

## Identical graph-safe output reuse

Each backend receives one persistent BF16 output tensor, allocated before capture. Each captured graph contains four sequential writes into that same backend-owned output tensor; every graph replay again writes into it. Inputs and weights remain immutable, output buffers are distinct across backends, and backend graphs are run serially on one CUDA stream. No output is read between the four writes. The final contents are checked against the reference before and after the long replay. This avoids a new output allocation per graph node or replay without introducing cross-backend aliases or concurrent writes.

The four backends use the same buffer ownership and capture structure. Triton writes directly into the supplied output tensor. The compiled PyTorch reference computes the same FP32 RMSNorm expression and copies into its supplied BF16 output tensor. Correctness checks include buffer identity and input/weight non-alias assertions. Any failed invariant stops the checkpoint before timing.

## Timing and sustained replay

First, capture one four-call graph for every backend and collect 401 randomized rounds. Each round contributes one replay interval for each of the four backends, so the latency phase retains **401 × 4 = 1,604 CUDA-event intervals per checkpoint**. Reported latency is the median graph event duration divided by four; the audit recomputes it from the retained raw durations.

Then run each backend's sustained graph by itself for a target of at least 30 seconds of CUDA-event time. The reusable block contains 32 sequential writes to that backend's same persistent output buffer. A short calibration estimates the event time per block. After a fixed 128-block pre-roll, a 128-block CUDA-event pilot estimates sustained block time. Each phase targets 30 adjacent approximately 1.1-second CUDA-event windows, giving about 33 seconds of event work per backend/checkpoint and headroom above the 30-second minimum; the calibrated graph-block replay count is retained for each window. The host enqueues every window without synchronizing between windows; one synchronization occurs after the final end event. This keeps the stream queued ahead of GPU execution. Record each window's event duration and replay count, plus the event-time gap between neighboring windows; a gap above 5 ms fails the phase. A window over 2 seconds is also a gate failure, and total phase time may not exceed 60 seconds. A 300-second per-checkpoint remote timeout is the hard bound for compilation, correctness, capture and all four sustained phases. The CUDA event intervals, window replay counts, host enqueue interval, backend order and actual total duration are retained.

The reported bandwidth is **logical input-plus-output GB/s**, computed as `(rows × width × 2 bytes × 2 directions × 32 calls_per_block × graph_blocks_replayed) / summed_event_seconds / 1e9`. It describes useful tensor bytes under this graph workload. NVIDIA SMI memory-busy percentage is a separate activity proxy; it is not a count of actual DRAM bytes and will not be reported as measured HBM bandwidth.

An in-process GPU-host sampler starts one persistent `nvidia-smi --loop=1` process after calibration and pre-roll, immediately before the measured phase; it stops after the final event completes and device synchronization. Each output row records the NVIDIA timestamp and parent monotonic arrival time, including duplicate readings. Each phase needs at least 25 timestamped query records and no query gap above 1.5 seconds. The raw record also stores monotonic phase start/end bounds, and the audit checks every included row against them. GPU busy, memory busy, VRAM used, power and temperature fields each need at least 95% finite-value coverage; otherwise the phase is ineligible for the sustained activity comparison. Samples outside that host-bounded event run are excluded from coverage and summaries. NVIDIA documents GPU and memory utilization as rolling measures over a device-dependent 1/6-to-1-second period ([NVIDIA SMI](https://docs.nvidia.com/deploy/nvidia-smi/index.html), [NVML utilization type](https://docs.nvidia.com/deploy/nvml-api/620/api/structnvmlUtilization__t.html)); one-second query records remain rolling-window readings, not independent sensor measurements. Keep all records, report the query cadence and repeated/unchanged readings separately, and never label the number of query rows as independent NVML samples. If telemetry is sparse, mark activity telemetry ineligible and retain the raw gap and readings; do not abort later backend compute or invalidate throughput when correctness, duration, CUDA-event adjacency and memory gates pass. Report query count, unique reading transitions, median and peak GPU busy, memory busy, power and VRAM, the largest query gap, and measured free/allocated/reserved CUDA memory. The phase UTC bounds, monotonic host bounds, event durations and included sample arrival times make the coverage filter auditable; individual event windows are retained as durations and are not assigned UTC timestamps.

## Memory budget and runtime estimate

At width 4,112, one BF16 input or output tensor is `32,768 × 4,112 × 2 = 269,484,032` bytes (0.25098 GiB). Four persistent output buffers use `1,077,936,128` bytes (1.00391 GiB). One input plus an FP32 reference adds `808,452,096` bytes (0.75293 GiB), giving `1,886,388,224` bytes (1.75684 GiB) for the modeled **persistent replay buffers** (input, four outputs and reference); the weight is 8,224 bytes. Fixture correctness temporarily allocates its own BF16 input and FP32 reference, so the measured `correctness_peak` snapshot is reported separately and is not represented by this persistent-buffer estimate. This explicitly counts one output per backend, not one output per captured operation or replay.

Before allocation, require at least 16 GiB free CUDA memory. Before timing, compute the additional maximum reserved-memory delta from the capture baseline and abort if it exceeds 8 GiB. The 8 GiB capture ceiling leaves room for compiled-reference workspace and allocator fragmentation beyond the 1.75684 GiB modeled live buffers. Record allocated, reserved, free and total bytes before allocation, after persistent buffers are allocated, after each graph capture and at the end of each phase. Check the same guards at the largest width before any long replay begins.

The bounded long phase is four backends × 33 seconds × 12 shape/seed checkpoints = **1,584 seconds (26.4 minutes) of target CUDA-event work**, with a 30-second gate floor. A 32-call graph block is expected to take about 5.8–7.3 ms from the issue #62 latency medians, giving about 151–190 block replays per 1.1-second window and roughly 4,530–5,700 blocks per backend/checkpoint. The prior 12-checkpoint study used 90.9 seconds of host runner time and 16.7 seconds of graph events; this draft estimates roughly 29–35 minutes total host wall time including the 26.4-minute replay workload, calibration, 1,604-interval latency phase, compilation, correctness, memory snapshots and telemetry. The 300-second per-unit timeout is the hard bound (60 minutes worst-case across all 12 units). A four-call latency graph at max width represents 2,155,872,256 logical input-plus-output bytes (2.00781 GiB); the 32-call sustained graph block represents 17,246,978,048 bytes (16.0625 GiB). The replay count for each of the 30 windows is stored individually; the audit recomputes total graph calls, logical bytes and throughput from those per-window counts. Partial checkpoint audits are allowed during execution; the final audit requires all 12 units, audits the attempt-receipt/checkpoint ID and SHA-256 links, compares candidate throughput with both registered comparators per seed, aggregates medians by width, and applies the 5% rule across every registered seed and width. Replay counts and nominal traffic are derived from actual calibrated event times and retained per backend. Logical traffic is not a claim about external HBM transactions because caching can change DRAM traffic.

## Checkpointing, source freeze and evidence

One `step.py` invocation runs or recovers exactly one width/seed checkpoint. `--status`, `--pause` and `--resume` are available; status distinguishes completed checkpoints from saved failures and names any blocking unit. Both this experiment's pause marker and the existing global vLLM pause marker are checked before attempt creation and again before remote submission. The parent H100 lock serializes jobs. Each remote result is cached atomically by the frozen source commit, width and seed, with three standard attempts per unit. For `s50-w4103` only, one narrowly scoped fourth attempt is permitted only when an operator explicitly invokes `--retry-transport-failures`, exactly three prior receipts for that unit all have outcome `transport_or_parse_failed`, and no checkpoint JSON exists. The fourth receipt records the override flag, prior attempt IDs and no-checkpoint precondition. This exception is limited to the exhausted first checkpoint and was added after the official proxy checksum was verified and a read-only SSH probe succeeded. After the manual fourth transport recovery, one fifth attempt is permitted only if the saved checkpoint is the audited candidate-phase telemetry-gap-only failure: all latency/correctness/memory/event-window checks passed, but the 1.5-second telemetry gap failed. Invoke only with `--retry-telemetry-only`; the archived checkpoint and attempt receipt must match the manifest SHA-256 links. The archive is validated before remote submission and remains immutable while the live checkpoint path is atomically replaced. No other fifth attempt is accepted; other failed or incomplete checkpoint JSON blocks subsequent units.

The source pin records the GPT-6 Luna delegated runtime, frozen source commit and SHA-256 for every compute, plan, telemetry, step and summary source. The runner checks these before submission and the audit verifies them against Git. Raw event intervals, replay counts, correctness fixtures, persistent-output pointer/alias evidence, memory snapshots, active-window samples and per-attempt receipts are committed checkpoint by checkpoint.

The first H100 checkpoint `s50-w4103` is preserved with all 1,604 latency intervals and its fourth attempt receipt. Correctness, memory, event duration and CUDA-event adjacency passed; the first candidate sustained phase was marked `gate_failed` solely because its maximum telemetry polling gap was 2.531 seconds against the frozen 1.5-second activity threshold. The phase remains ineligible for activity claims; this evidence does not establish an invalid throughput measurement. Its checkpoint and receipt are archived with SHA-256 links. The narrowly gated fifth manual attempt exists to rerun that checkpoint after root review; until it is authorized and audited, no later unit may start.
